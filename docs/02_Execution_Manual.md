# 开发流程与执行手册 SOP

[返回主页](../README.md) · [企划书指南](01_Project_Plan_Guide.md) · [事实来源政策](03_Source_of_Truth_Policy.md)

## 1. 目的与角色

本手册规定一个模块从计划到验收的标准作业。目标是使每次交付范围明确、证据可检查、责任可追踪，并让返工回到同一模块内完成。

| 角色 | 主要责任 | 交付物 |
| --- | --- | --- |
| 项目负责人 | 确定目标与边界、传递资料、决定阶段放行及操作授权 | 批准记录、范围决策、模块验收记录 |
| 开发端（默认 Codex） | 调研、计划、实现、测试、QC1 自检、整理证据 | Implementation Plan、实现、Completion Report、Review Bundle |
| 审核端（默认 GPT） | 独立检查计划与实现，指出问题并复核修复 | 审核结论、问题清单、修复 Prompt、允许的下一阶段 |

Review Bundle 是交给审核者的版本固定审核包。它是实现证据的交付格式，不能用摘要代替完整改动。工具无法读取的文件、无法执行的验证或缺失资料必须明示。

## 2. 开工前：建立基线和会话边界

1. 依据[企划书指南](01_Project_Plan_Guide.md)编写长期企划书和项目执行手册。
2. 两份文件经独立审核与负责人确认，记录版本和适用范围。
3. 选择一个依赖已满足的模块，填写目标、范围、非目标和验收标准。
4. 为该模块分别建立开发会话与审核会话。两边使用相同的文档版本与模块编号。
5. 核对工作目录、分支、已有改动和实际项目状态。保留他人改动；不为得到“干净状态”擅自删除或还原内容。
6. 只读取当前模块需要的规范章节、代码、测试、官方资料和相关 Skill；缺少必需资料时记录阻塞。

模块分会话是上下文管理方式，不是并行开发多个模块的默认授权。一个模块完成验收后，才由负责人选择并启动下一个模块。

## 3. 阶段门槛与放行条件

`PASS ✅` 表示注明阶段和版本的材料满足审核要求；`CHANGES REQUIRED ⚠️` 表示必须修订或补证。负责人授权决定可执行动作，二者分开记录。

| 门槛 | 输入 | 放行条件 | 通过后的位置 |
| --- | --- | --- | --- |
| G0：规划基线 | 企划书、项目执行手册 | 目标、架构、顺序与验收一致；独立审核通过，负责人确认 | 可以编写当前模块计划 |
| G1：Plan Gate | 当前模块计划与来源清单 | 范围、依赖、契约、风险、验证和验收明确；独立审核通过 | 停在待实现；负责人放行后才能实现 |
| G2：QC1 / 交付检查 | 完整改动与验证结果 | 开发端自检和修复完成，必要检查通过，审核包完整且对应实际版本 | 提交审核包后停止，等待 QC2 |
| G3：QC2 / 实现审核 | 审核包、基线文件与已批准计划 | 独立检查通过，验收逐项有证据，阻断问题全部关闭 | 待负责人授权收尾 |
| G4：Module Gate | 审核结论、授权收尾结果、最终版本 | 所需收尾已完成，文档与状态一致，回退办法明确；负责人验收 | 当前模块关闭并停止 |

采用 PR 的项目，将第 9 节的检查纳入 G4。没有 PR 流程的项目，也必须记录实际交付版本与负责人验收。

不使用“有条件通过”代替阻断问题的关闭。非阻断改进可以登记，但不能把失败的必要验收项降级为未来建议。

必要检查失败或无法执行时，可以交付问题材料供诊断，但须标记为“阻塞 / 未满足 G2”，不能当作已完成的验收交付。

## 4. 单模块标准作业

| 步骤 | 开发端动作 | 检查与产出 |
| --- | --- | --- |
| 1. 定义任务 | 核对模块、依赖、范围和验收 | 模块任务卡与当前文档版本 |
| 2. 核验来源 | 读取相关官方指南、案例、参考说明及图示 | 来源清单；待确认项与影响范围 |
| 3. 编写计划 | 说明改动文件、架构、风险、测试与回退 | Implementation Plan；尚不修改实现 |
| 4. 审核计划 | 根据审核反馈修订，必要时同步范围与基线 | G1 结论及对应计划版本；不通过则返回步骤 3 |
| 5. 负责人放行 | 核对批准与本次执行范围 | 实现授权记录；使用独立模块分支 |
| 6. 实现 | 只完成当前模块，遵守依赖与权限边界 | 实现与必要测试；范围变化返回 G1 |
| 7. 验证 | 执行适用测试、异常注入及界面验证 | 命令、环境、预期、实际与证据位置 |
| 8. QC1 | 检查当前模块相对基线的全部变化，修复发现 | 自检清单；修复后重跑受影响验证 |
| 9. 更新记录 | 更新必要 Skill、文档、架构决策与状态 | 变更摘要，明确仍是“待独立审核” |
| 10. 打包并停止 | 输出完成报告和审核包，核对版本 | 满足 G2 后等待审核；未满足则报告阻塞，不自动提交或推进 |
| 11. QC2 | 审核端检查原始证据并对照计划 | G3 结论；不通过则在本模块修复并生成新版包 |
| 12. 收尾与验收 | 按负责人授权执行收尾，核对最终版本 | G4 记录，关闭当前模块并停止 |

正常循环为：**Plan → Plan Review → 负责人放行 → Implement → Test → Failure Test → UI Verify → Self Review → Update Skill/Docs → Bundle → STOP → Independent Review**。测试、故障与界面步骤按下节判断适用性；停止不是取消修复责任，而是等待对应审核或放行。

### 4.1 Implementation Plan 必须包含什么

- Goal、Scope、Out of Scope、Dependencies，以及对应基线文档版本。
- 实际读取的来源清单；指南、完整案例、参考说明、错误与状态、限制、兼容性及图示的核验记录。
- 预计新增、修改、删除的文件；对现有架构的接入方式、状态和数据所有权。
- 风险及其阻断措施，特别是并发、未知结果、持久化、安全和数据一致性。
- 如有第三方参考，列出来源版本、文件或模式、许可与复用级别。
- Testing Plan、逐项 Acceptance Criteria（验收标准）、回退与恢复办法。
- 未解决事项、影响范围与需要负责人决定的问题。

无外部依赖或无第三方复用时明确说明，不虚构来源或复用记录。

### 4.2 实现时的通用约束

保持已批准架构的依赖方向与权限边界。受控外部组件通过项目指定的适配层访问；界面不能绕过业务规则和后端授权。具体分层以目标项目的批准设计为准。

高风险写入应有明确的责任组件和前置检查。未知结果不等于失败，也不等于成功；先确认外部状态，避免重复产生副作用。关键记录无法持久化时，按设计阻止相关高风险操作，保留适当的观察与恢复能力。

不把秘密写入源码、版本记录、日志、测试样本、报告或截图。不要引入与本模块无关的依赖、重构或后续模块功能；必要的范围变化先回到计划审核。

## 5. 验证与 QC1 标准

### 5.1 验证适用性矩阵

| 检查 | 验证目标 | 何时适用 |
| --- | --- | --- |
| Unit | 内部规则、计算、状态转换与边界 | 存在可独立验证的逻辑时 |
| Contract | 输入输出、字段、枚举、错误与状态符合约定 | 引入或修改组件边界、外部依赖时 |
| Integration | 当前模块与相邻层实际组合正确 | 改变组件协作或数据链路时 |
| Failure Injection | 异常下能阻断、恢复并保留一致状态 | 高风险操作及关键状态、并发、存储或连接路径 |
| UI Verification | 真实界面中的数据、状态与操作符合预期 | 模块新增或影响用户可见界面时 |
| 文档与静态检查 | 链接、术语、示例、来源与规范一致 | 文档变更适用；纯文档无需虚构运行测试 |

每项只能记录 `PASS / FAIL / NOT RUN / NOT APPLICABLE`。`NOT RUN` 表示未执行并写明原因；`NOT APPLICABLE` 必须说明为何与本次改动无关。必要检查未执行或失败时，不得把模块标为已验收。

异常场景按风险选择：超时、断连、重复或乱序事件、过期数据、未知状态、持久化失败、回调异常、限速、重连和重启恢复。测试应检查可观察结果，例如“未知结果后没有第二次副作用”，而不只是“没有抛错”。真实环境或有副作用的验证须使用负责人已批准的环境与范围。

### 5.2 界面验证

适用时实际启动系统并检查：页面可打开、数据与状态正确、错误可见、未知不显示为正常、过期不显示为新鲜、禁止操作的原因清楚、导航可用、没有影响流程的严重控制台错误。保存已脱敏证据与运行版本。

完全没有界面影响时，记录 `UI Verification: NOT APPLICABLE` 和原因。启动失败或无法访问时记录 `NOT RUN`，不能以静态阅读冒充实际检查。

### 5.3 开发端完整改动自检

检查当前模块相对批准基线的**全部变化**，覆盖实现、测试、配置、依赖、文档、删除文件和新文件。仅查看最后一次修改或少量片段不算完整自检。

重点检查：缺陷、安全与权限、竞态、外部契约、Fail-Closed、秘密泄露、重复逻辑、死代码、遗漏测试、异常处理、状态一致性、恢复行为、过度设计、不必要依赖及第三方许可义务。修复后重新执行受影响验证；最终审核包必须反映修复后的版本。

## 6. 审核包交付规范

### 6.1 包含哪些内容

建议命名：`Mx-review-r01.zip`，修复后递增修订号，不覆盖旧审核记录。输出到负责人指定的目录；未指定时可放桌面，并在完成报告提供准确位置。以下是目标项目产物的逻辑结构，可按项目调整：

```text
Mx-review-r01/
├── MANIFEST.md
├── IMPLEMENTATION_PLAN.md
├── COMPLETION_REPORT.md
├── REVIEW.patch
├── FILES/                    # 新文件及补充上下文、必要完整文件
├── EVIDENCE/                 # 测试记录、适用的界面证据
└── REVIEW_HISTORY.md         # 计划结论、历史问题及本轮修复对应关系
```

另提供版本固定的企划书、执行手册、相关 ADR 与来源清单，或提供审核端确实可访问的精确版本位置。不能只写“见本地文件”而让审核端猜测内容。

纯文本改动需提供完整 patch；新文件、二进制、删除与重命名都要在清单中列出，patch 无法表达的内容另给可审核副本。补充必要的基线上下文，确保审核端能够理解受影响契约与相邻层。缺少基线时可提供批准范围的完整文件快照，不能声称只凭 diff 就完成全链路核验。

### 6.2 Manifest 最小字段

```markdown
# Review Manifest

- Project：[项目名称]
- Module：[Mx — 名称]
- Bundle Revision：[r01]
- Created At：[日期、时间、时区]
- Branch：[实际分支]
- Base Revision：[相对哪个批准的提交；新项目尚无提交时明确说明]
- Head Revision：[实际提交；无新增提交时不伪造]
- Workspace State：[干净 / 含已暂存、未暂存或未跟踪改动]
- Snapshot ID：[由本轮交付文件的内容清单校验值标识]
- Baseline Documents：[企划书、手册、ADR 的版本及可访问位置]
- Approved Plan / Review：[计划修订、审核结论与负责人放行记录]
- File Inventory：[全部新增、修改、删除、重命名与必要上下文]
- Payload Checksums：[交付文件逐项路径与 SHA-256；不包含清单自身]
- Verification Environment：[系统、运行环境、依赖锁定信息]
- Test Evidence：[命令、预期、实际、状态、日志位置]
- Exclusions：[遗漏或脱敏的内容、原因及其审核影响]
- Open Issues：[含阻断与待确认项]
```

**未提交改动也必须可定位。** 只记录分支名和 Head Revision 不足以识别工作区版本：patch 应覆盖相对 Base Revision 的模块累计变化，包含已提交、已暂存与未暂存内容；未跟踪文件单独纳入文件清单与内容校验。打包后核对包内文件，避免报告和 patch 来自不同修订。

Snapshot ID 可采用文件内容校验清单的整体摘要；压缩包自身的 SHA-256 放在外部完成报告中，便于确认传递前后内容一致。校验值用于标识内容，不等于质量通过或来源可信。

不为打包而自动 commit。可以在负责人批准的范围内交付未提交快照。敏感内容必须排除或脱敏，同时说明审核受限之处；必要证据受限时不能伪造完整覆盖。

### 6.3 完成报告结构

```markdown
# Completion Report — [模块编号] / [修订号]

## Executive Summary
## Approved Scope / Plan Revision
## Sources Used / Visual Review
## Implementation / Architecture Impact
## Files Created / Modified / Deleted
## OSS Reuse / License / Reuse Level
## Tests / Failure Injection
## UI Verification
## Self Review Findings / Fixes
## Skill Changes — Added / Modified / Removed / Pending
## Docs / ADR Changes
## Git Status / Bundle Location / Snapshot ID / Archive SHA-256
## Open Issues / 待确认
## Acceptance Criteria — 逐项结果与证据
## Recommended Next Module — 仅建议，不执行
```

## 7. QC2 独立审核与返工

使用[审核端模板](../prompts/Reviewer_Prompt_Template.md)，先核对材料身份与版本，再读完整改动、必要上下文及测试证据。审核端分别说明哪些结果由自己复现，哪些仅核对了开发端提交的记录。

如有问题，输出 `CHANGES REQUIRED ⚠️`，列出问题编号、严重程度、文件或章节位置、触发场景、原因、影响、修复方向及验证要求，并附可复制给开发端的修复 Prompt。

开发端收到反馈后，在当前模块内修复，逐项回应问题编号，重新验证并生成新版报告与审核包。审核端既复核原问题，也检查修复引入的变化；不能只看到“已修复”三个字便通过。

审核后发生相关改动时，原 PASS 对新内容不再成立。更新版本、证据与审核结论；如果方案、范围、契约或风险设计变化，先回到 G1，再做实现审核。即使是文档修订，也应识别它是否改变了已审核的行为要求。

## 8. Skill、文档和实时状态

Skill 仅按[事实来源政策](03_Source_of_Truth_Policy.md)记录已验证经验。必要时更新架构、运行手册、ADR、契约说明和模块文档；不为满足清单创建空文档。

在目标项目的状态文件中至少记录以下字段：

```markdown
# Project Status

- Current Phase：[计划待审 / 计划修订 / 待实现放行 / 实现中 / 实现待审 / 实现修订 / 待收尾 / 待验收 / 已验收]
- Current Module：[编号与名称]
- Baseline Documents：[实际版本]
- Approved Plan：[修订号与审核记录]
- Branch / Base / Head / Snapshot：[实际值；缺失时如实说明]
- Review Bundle：[位置与修订号]
- Review Result：[阶段、结论、所对应版本]
- Completed：[已完成且有证据的内容]
- Tests：[结果及证据位置；含未执行项]
- Open Issues：[问题编号、影响、责任人]
- Blocked：[阻塞原因；无则说明]
- Authorized Next Action：[负责人已明确授权的下一动作；没有则写等待]
- Next Candidate：[建议的下一模块；不是执行授权]
```

新会话从实际状态、当前改动和审核记录恢复上下文。状态文件与证据不一致时先核对，不因它叫“状态文件”就覆盖实际事实。长期企划书只在设计变化时修订，不写入今日进度。

## 9. Git 与可选 PR 收尾

每个模块使用独立分支，例如 `feat/mx-module-name`。开始前核对已有改动，结束前报告 Git 状态。默认完成后停止，不自动 commit、push、创建 PR、merge 或进入下一模块。

G3 通过后，负责人可以一次授权多个连续收尾动作；在明确授权范围内执行，无需把同一授权拆成反复确认。操作前仍需核对相关审核版本和当前改动一致。

采用 PR 的项目，标准收尾顺序为：

1. 按授权提交、推送并创建 PR，关联模块计划、完成报告和审核证据。
2. 独立审核 PR 的实际改动，核对持续集成（CI）及项目要求的检查结果。
3. 有修复则提交新版本，重跑受影响检查并重新审核。旧提交的绿灯不能覆盖新增改动。
4. 审核与必要检查通过后，按负责人适用的授权合并。
5. 核对合并后的实际版本，执行与变化相关的验证，确认文档和状态一致，再完成 G4。

没有配置某项检查时如实说明；必要检查缺失应补齐或由负责人正式调整验收政策，不能默认为已通过。

## 10. 最终验收与停止清单

- [ ] 当前模块范围完成，非目标未混入，依赖有证据。
- [ ] 计划审核、负责人实现放行和 QC2 对应明确版本。
- [ ] 验收条件逐项通过，必要测试和界面验证有真实证据。
- [ ] 阻断问题与关键待确认项已解决，修复已经重审。
- [ ] Skill、相关文档与状态已经按需更新。
