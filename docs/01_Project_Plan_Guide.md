# 项目长期企划书指南

[返回主页](../README.md) · [执行手册](02_Execution_Manual.md) · [事实来源政策](03_Source_of_Truth_Policy.md)

## 1. 三类文件各负其责

| 文件 | 回答的问题 | 更新时机 |
| --- | --- | --- |
| 长期企划书 | 系统为什么存在，做什么，长期边界是什么 | 目标、范围、架构或长期约束发生经批准的变化时 |
| 项目执行手册 | 按什么顺序开发，每个模块怎样验收 | 模块拆分、依赖、作业方法或验收流程变化时 |
| 项目状态文件 | 当前做到哪里，有什么证据，下一步等待什么 | 阶段变化、审核、修复与交接时 |

长期企划书是设计基线，不是进度日报。Markdown 可作为可版本追踪的主版本；若需要 PDF，则从相同版本导出，并标注文档版本与对应提交，避免出现两份独立维护的正文。

本页提供的是写作指南。以下建议路径位于**目标项目**，不表示这些文件已经存在于本方法库。

## 2. 推荐的企划书结构

| 章节 | 必须说明的内容 |
| --- | --- |
| 文档控制 | 项目名称、负责人、版本、修订原因、审核状态、对应基线 |
| 执行摘要 | 目标用户、核心问题、预期交付物、成功标准 |
| 目标与非目标 | 首期包含什么，明确排除什么，后续扩展的前提 |
| 使用场景 | 正常流程、异常流程、人工决策点、可恢复方式 |
| 系统边界 | 输入输出、受控资源、外部依赖、权限与责任边界 |
| 架构原则 | 分层职责、依赖方向、读写边界、状态与数据所有权 |
| 质量属性 | 安全、可靠性、可观测性、可维护性及可检查的要求 |
| 数据与状态 | 关键实体、状态转换、持久化、一致性、恢复与保留策略 |
| 模块路线图 | 模块目标、范围、非目标、依赖、交付物与验收条件 |
| 验证与运行 | 测试策略、故障处理、备份恢复、发布和回滚原则 |
| 来源与复用 | 权威资料入口、版本核验方法、开源复用治理 |
| 决策与待确认 | 已批准的架构决策、未确认事项、影响与解决责任人 |

“性能良好”“足够安全”不能单独作为验收条件。写成在特定场景、输入与环境下可以检查的行为，例如：“重复收到同一事件时，最终只产生一次有效状态更新”。具体数值应来自目标项目需求，不能把示例数值直接当作行业标准。

## 3. 模块划分方法

### 3.1 一个模块应当可独立说明、验证和审核

每个模块都要回答六个问题：解决什么问题、包含什么、排除什么、依赖什么、交付什么、如何判断完成。

优先围绕一个明确能力或最小可验证的业务切片拆分。模块既可以是一项基础能力，也可以连接界面、业务逻辑和存储；不必机械地按技术层各建一个巨型模块。

如果同一模块包含多个互不依赖的目标，或审核者无法在一个审核周期内理解全部变化，先拆成 `Mx.1`、`Mx.2` 等子模块。拆分仍需保留父模块边界，并确认各自的依赖和门槛。

### 3.2 用依赖决定顺序

建议先建立可运行、可观察、可回退的基础，再逐步解锁更高风险能力。以下是可调整的通用顺序，不是所有项目必须照搬的模块编号：

```text
需求与来源校准
→ 工程基础、配置与秘密隔离
→ 最小交互骨架或可观察入口（适用时）
→ 只读或低风险业务切片
→ 状态管理、持久化与异常恢复
→ 受控写入与业务编排
→ 完整流程验证
→ 发布、运维与回滚演练
```

依赖没有完成时，不把缺失能力偷偷实现进当前模块。记录阻塞；由负责人决定调整顺序、拆分或重新审批。模块验收证明可进入下一道流程，不直接授权真实环境操作。

### 3.3 模块定义模板

```markdown
## Mx — [模块名称]

- Goal：[需要解决的问题与用户价值]
- Scope：[本次包含的能力]
- Out of Scope：[明确不做的能力]
- Dependencies：[前置模块及其验收证据]
- Inputs / Outputs：[输入、输出与边界契约]
- Ownership：[状态、数据、权限的归属]
- Deliverables：[实现、测试、文档、审核资料]
- Risks：[关键风险及其阻断措施]
- Acceptance Criteria：
  - AC-01：[场景、预期行为、验证方法]
  - AC-02：[关键失败场景、预期行为、验证方法]
- Rollback / Recovery：[回退与恢复办法]
```

## 4. 两份基线文件的校准流程

1. 开发端编写长期企划书与项目执行手册初稿，注明版本；未确认内容显式标记。
2. 负责人把同一版本交给独立审核端，检查目标、架构、模块顺序、风险与验收是否相互一致。
3. 审核端给出 `PASS ✅` 或 `CHANGES REQUIRED ⚠️`，问题应定位到章节或模块，并提供修改方向。
4. 开发端修订两份文件，说明改动及影响；涉及范围、依赖的变化必须同步检查关联章节。
5. 两份文件均通过审核且负责人确认后，冻结为开发基线，进入第一个模块的 Implementation Plan（实施计划）。

冻结表示后续变化需要追踪和审核，不表示永远不能修改。文档通过也不意味着后续模块的计划已经通过。

## 5. 在目标项目内建立最小文档集合

| 建议路径 | 职责 |
| --- | --- |
| `docs/PROJECT_PLAN.md` | 长期目标、边界与架构原则 |
| `docs/EXECUTION_MANUAL.md` | 项目自己的模块顺序和执行门槛 |
| `docs/MODULE_ROADMAP.md` | 模块定义和依赖；也可并入执行手册 |
| `docs/SOURCE_OF_TRUTH_POLICY.md` | 按本仓库政策适配的项目来源规则 |
| `docs/PROJECT_STATUS.md` | 实时状态、版本与下一动作 |
| `docs/adr/` | 重要架构决策记录（ADR）及其变更原因 |
| `docs/references/REUSE_MATRIX.md` | 第三方复用决策与验证记录 |

这些是建议名称。项目已有同职责文件时沿用原路径，在 Prompt 中填写真实位置；不要为了符合模板建立重复的事实来源。Skill 是保存已验证经验的可复用指引，可按需采用，不是开工的必需空文件。

## 6. 企划书发布前检查

- [ ] 目标、非目标和首期范围清楚，没有混入实时进度。
- [ ] 模块都有依赖与验收条件，编号在两份基线文件中一致。
- [ ] 架构责任、权限和数据所有权明确，异常路径能够解释。
- [ ] 高风险操作的阻断、恢复和人工决策条件明确。
- [ ] 事实有来源，工程选择有理由，待确认事项有解决路径。
- [ ] 开发端与审核端使用同一文档版本，修改记录可追踪。
- [ ] 独立审核结论与负责人确认已经记录。
