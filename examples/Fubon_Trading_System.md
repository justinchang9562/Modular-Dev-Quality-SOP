# 案例：富邦半自动交易系统

[返回方法论主页](../README.md) · [通用执行手册](../docs/02_Execution_Manual.md)

本页以用户提供的“富邦新一代 API 半自动交易系统”规划与协作实践，说明通用方法如何适配具体项目。这里记录的是**案例中的设计要求与开发方法**，不宣称系统已经全部实现、验收或上线，也不构成投资建议。

## 1. 背景与资料边界

案例面向个人使用的证券半自动交易系统，涉及行情、帐务、状态管理、风险检查、人工批准与受控执行。由于外部状态、连接与持久化异常可能产生真实影响，开发者先建立长期规划，再按模块实现和审核。

整理依据：

- 用户提供的工作流说明与开发、审核 Prompt 原稿。
- 桌面参考文件《富邦新一代 API 半自动交易系统工程企划书》：长期目标、系统边界、架构、安全、测试、运行与回滚原则；重点参考第 1、3、5、10、11、17 章。
- 桌面参考文件《富邦半自动交易系统：开发流程与执行手册》：模块顺序、固定开发循环、门槛、复用治理和上下文策略；重点参考第 1、3、10—14、18 章。

原始 PDF 未收录于本仓库；其中的具体参数、状态码和兼容版本不作为当前官方事实在此复述。两份材料的路线图粒度不同，不将其模块编号拼接成一份未经确认的现行计划。本案例也未核验原项目仓库的当前进度。

## 2. 如何采用通用流程

| 案例中的动作 | 对应的通用方法 |
| --- | --- |
| Codex 编写项目企划书与开发执行手册，交给 GPT 往返校验 | 先校准目标与作业基线，再进入开发 |
| 两端分别按 Module 新建开发窗口和审核会话 | 按模块隔离上下文，并共享相同文档版本 |
| Codex 先提交 Implementation Plan | 通过 Plan Gate 控制范围、来源与风险 |
| GPT 检查方案，反馈 PASS 或修复 Prompt | 在实现前发现设计缺陷并闭环修订 |
| 负责人确认后，Codex 只实现当前模块 | 限制在制品，防止越界开发 |
| 实现后执行测试、异常注入、界面验证与完整 diff 自检 | QC1 将质量检查纳入开发过程 |
| Codex 在桌面生成报告和 Review Bundle，负责人转交 GPT | 用可传递、可定位版本的资料执行 QC2 |
| 不通过则修复、重测并生成新版审核包 | 返工留在同一模块，旧结论不覆盖新改动 |
| 通过后由负责人安排收尾与 Module Gate | 技术审核与操作授权分开 |

如果项目使用 PR，还需核对 PR 对应版本、独立审核、CI/Checks 与合并后结果；开发窗口与审核窗口的分离不会自动授予并行开发或合并权限。

## 3. 本案例独有的约束

以下约束属于案例的项目设计，不能直接移植成所有行业的硬性规定：

- **官方资料入口。** 案例要求以富邦当前官方资料核验行为，从 `llms.txt` 定位相关页面，必要时用 `llms-full.txt` 搜索与查漏；还需阅读相关 SDK 使用教学、完整案例、Reference 和有行为意义的 HTML 图示。
- **SDK 访问隔离。** 按本案例给出的开发规范，由明确授权的 Fubon Broker Adapter 访问 Fubon Neo SDK。Frontend、Application Layer、Strategy、Draft、Risk、Approval 等模块不能直接 import 或调用该 SDK；真实写操作通过受控的 Execution Engine → Broker Adapter 链路。
- **人工批准与风控。** 真实新单、改单、删单需要明确人工确认，不能绕过 Risk、Approval 或执行责任组件。批准不能只依靠界面隐藏按钮。
- **Fail-Closed 与未知结果。** 断线、过期行情、关键持久化失败、未知订单状态或未解释的对账差异，应按项目设计阻断相应高风险操作。未知结果先查询和核实，不能自动重送。
- **分阶段验证。** 案例区分模拟、官方测试、Shadow 与受控真实运行阶段；具体解锁条件由该项目当前批准规范确定。
- **敏感资料保护。** 凭证、密码、Secret 与未脱敏帐务资料不能进入源码、Git、日志、测试样本、审核包或截图。

这些是项目要求的记录，不是对富邦当前产品行为的独立验证。实际实施时仍须重新核对适用的官方资料与项目基线。

## 4. 一个模块的审核闭环示意

以“状态与异常恢复”模块为例，不预设它在现行路线图中的编号：

1. 明确本模块只处理已批准的状态转换、事件去重与恢复，不顺手加入新的交易功能。
2. 读取相关官方指南、状态说明、回报与查询流程及图示，保留适用版本与来源清单。
3. 在 Implementation Plan 中说明责任组件、持久化、未知结果处理、文件改动和验收条件。
4. GPT 审核计划；如发现竞态或 fail-open 风险，返回具体修复要求。负责人放行后才能实现。
5. Codex 实现，并按风险注入超时、重复回报、断线、数据库失败及重启场景；界面有影响时实际验证状态展示。
6. QC1 检查本模块完整累计改动，修复并重测，生成带 manifest、patch、文件清单和证据的审核包。
7. GPT 针对该包执行 QC2；不通过则留在本模块修复并重新打包，通过则等待负责人安排收尾。

例如，验收可以要求“未知提交结果后，不会自动产生第二次提交；恢复过程有可检查的状态与记录”。这是案例中的验收设计示意，不能写成某次测试已经通过。

## 5. 从案例提炼出的通用规则

| 项目特定做法 | 可迁移的规则 |
| --- | --- |
| 读取富邦官方索引、SDK 教学、案例与参考说明 | 从权威入口发现资料，先理解完整流程，再核对精确契约 |
| 通过受控适配层调用 SDK | 明确受控资源的访问边界和责任归属 |
| 交易写操作经过风控与人工批准 | 高风险副作用应有前置检查和明确授权链 |
| 未知订单先查询、对账，不自动重送 | 结果未知时先确认状态，避免重复副作用 |
| Shadow 阶段禁止真实写入 | 在产生真实影响前，用受控环境验证完整流程 |
| 两端按模块协作，版本固定后送审 | 小批量交付、独立质检、可追溯与明确停止点 |

复用本方法时，把本项目的业务约束留在目标项目规范或独立案例中；主干指南和 Prompt 只保留可以跨项目使用的流程与检查方法。
